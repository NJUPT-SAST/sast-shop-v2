# 管理员后台

桌面站新增 `/admin`，复用现有 Next.js、共享 shadcn/Radix 组件、飞书登录、ConnectRPC、Bun/PostgreSQL 和后台任务。没有引入另一套用户体系或通用 CMS，也没有增加前端依赖。原商城页面路径与普通用户协作维护店铺、商品模板的权限保留。

## 权限与入口

- 普通用户继续使用商城和协作维护功能；后台 API 在服务端校验管理员身份。
- 店铺、商品模板的协作写接口和默认图片上传允许活跃的 `user`、`admin`、`superadmin`；无效身份或非活跃账号返回未认证错误，缺失或未知角色拒绝写入。显式配置的上传角色白名单仍按配置执行。普通端删除商品模板仍限创建者，管理员全局治理走后台接口。
- 管理员处理用户封禁/解封、全局商品治理、订单、账单、采购任务和西口袋异常。
- 只有超级管理员能授予/撤销管理员和超级管理员权限。不能撤销或封禁最后一名有效超级管理员；普通管理员不能通过封禁管理员绕过授权边界。
- 封禁是全面封禁，用户无法继续操作已有交易。后台以实际管理员身份处理，不冒充原用户。
- 会话每次读取数据库当前角色、状态、授权版本。封禁、解封和授权变化会让旧会话永久失效，必须重新登录。
- 飞书客户端使用已有免登流程，普通浏览器使用已有飞书 OAuth。后台会先获取实时管理员上下文，按角色渲染入口；前端隐藏按钮不代替后端权限检查。

## 业务范围

| 模块 | 首版能力 |
| --- | --- |
| 概览 | 按各业务域汇总用户、商品、订单、待核实款项与异常任务 |
| 用户 | 搜索/筛选、详情、封禁/解封、超级管理员授权 |
| 店铺/商品模板 | 保留协作维护，管理员全局新增、修改、封锁/解封 |
| 现货 | 全局商品治理、订单查询、实际履约完成、整单取消/撤销完成/恢复 |
| 采购 | 需求和任务查询、取消、按原编号恢复、整单撤销完成、历史分配补录 |
| 账单 | 查询当前及历史轮次、待核实付款确认/驳回、完整款项历史 |
| 西口袋 | 活动/账单/任务查询、符合状态规则的取消与整单纠错、失败任务及通知重试 |
| 纠错记录 | 预览、确认、步骤状态、失败原因、同一操作续执行 |
| 审计 | 操作人、时间、请求编号、原因、依据、前后快照及对象关联 |

西口袋后台不展示人脸数据、私有照片、对象存储地址、支付二维码或识别结果原始载荷。管理员任务入口只允许明确列出的运营任务类型。

## 整单纠错规则

订单编号保持不变，成功纠错后进入新的 `lifecycle_round`。旧账单保留为历史，当前轮次重新建立账单关系；已收到且决定保留的款项关联原始付款，不要求用户重复支付。普通端所有交易写入携带页面原先读取的处理轮次，旧页面、旧链接、旧异步回调不能修改恢复后的交易。

每次强干预需填写原因、核实依据，先生成有有效期的预览，显示影响范围、款项处理和恢复字段，再执行。预览校验资源版本与全部关联账单版本；过期或变化后需重新核查。允许单个管理员执行，不增加第二人审批。

款项处理区分：

- `no_payment_received`：核实未收到款项。
- `retain`：保留有效的原到账款项，继续履约。
- `refunded`：已经在线下完成全额退款，登记核实记录。
- `confirmation_error`：原收款确认有误、实际没有到账，撤销错误确认，不伪造退款记录。

同一任务同时包含已确认收款和仅申报付款时，款项方式处理已确认部分；其余申报必须逐笔核实未到账并主动勾选确认。实际已到账的申报应先确认收款，再生成整单预览。

有关联交易的退款必须从源订单/任务/活动执行，联动履约与账单状态。仅无业务源的独立账单允许单独登记全额退款。首版不包含部分商品冲正、部分退货和部分退款，也不调用转账/退款渠道。

历史取消记录缺少库存或分配快照时，后台提供显式恢复字段，由管理员依据原始记录填写，服务端校验参与者、商品、数量、金额和其他任务占用后执行。不能直接覆盖任意数据库字段。

## 一致性与恢复

复用 PostgreSQL 保存纠错步骤和执行租约。业务记录先被当前纠错占用；跨服务账单变化使用内部认证、固定操作编号和幂等结果表；本地更新、审计和步骤进度在同一事务提交。网络结果未知时保留占用，通过原请求编号查询和续执行，不创建第二次纠错。

后台任务自动继续暂时失败的步骤，达到尝试上限或权限变化后转为需人工处理。可由有权管理员接管同一记录。确定未产生任何已完成步骤的版本冲突会释放占用；现货预留库存使用独立逆向流水补偿，避免再次预览重复扣库存。过期执行者不能释放新执行者的资源。

采购收款回调使用持久 outbox 重试，并携带处理轮次；历史账单的回调不会改变当前任务。无应收账单的纯自购任务/活动不适用撤销收款完成，可按实际需要取消或恢复整单。不要通过直接改状态、删账单、删纠错记录来解除占用。

## 部署步骤

1. 备份数据库并确认已有 `001_init.sql` 和 `002_west_pocket.sql`。本次仅增量执行 `005` 至 `009`，不能重跑初始化。已有 `003/004` 保持原部署状态。
2. 对目标数据库运行 `DATABASE_URL=... make migrate-admin`。每份迁移有事务；命令遇错停止。它是一次性升级命令，不是可重复的迁移管理器；部分成功后按实际已执行文件继续。
3. 为 payment、spot、errand、westpocket 服务配置相同的高熵 `ADMIN_INTERNAL_TOKEN`（至少 32 字符），只保存在服务器环境。沿用 `PAYMENT_SERVICE_URL/PORT`。西口袋原内部 token 和私有云服务配置仍按其接入文档提供。
4. 部署六个后端服务和桌面、移动前端。移动端也必须同步发布处理轮次支持。兼容旧客户端仅限第一轮；恢复后的交易会拒绝缺少有效轮次的旧写请求。
5. 参照仓库中的 `deploy/Caddyfile.local` 更新实际公网网关，按服务白名单开放六个 `*AdminService`；剥离客户端的 `X-Admin-Internal-Token` 和 `X-West-Pocket-Token`。不得把整个 admin/payment/errand 命名空间通配转发到内部 RPC。当前实现沿用六服务共库、共享数据库账号的部署方式。身份和关联商品的 `FOR SHARE` 行锁除了 SELECT 还需要相应 UPDATE 权限，不能仅授予跨 schema 只读权限。分库/严格分账号部署需先适配事务和授权，不在本次部署模板中直接支持。
6. 在既有飞书应用配置桌面站 OAuth 回调和可访问域名。前端沿用当前认证变量，无需把内部 token 放进前端环境。
7. 核实首位超级管理员的已有活跃用户 ID，在后端环境运行：

   ```sh
   go run ./internal/service/userservice/cmd/bootstrap-admin \
     --user-id 123 --reason '首次启用管理员后台' --operator '经核实的运维人员'
   ```

   初始化会写审计并撤销该用户原会话。只允许首次初始化；后续授权在后台由超级管理员执行。
8. 先验证登录、只读查询和角色边界，再用可控测试订单验收取消、退款登记、恢复、任务重试及普通端旧页面拒绝。代码合并和本地测试不代表生产已经迁移、配置或发布。

## 验证命令

后端遵循现有 Go workspace 与 Buf 生成流程。集成测试使用专用 PostgreSQL 地址，自动创建/删除独立测试数据库；不要指向不允许创建测试数据库的生产环境。

西口袋和采购纠错测试仅加载业务所需迁移，可使用普通 PostgreSQL 运行。以下全量命令还包含商品全文检索测试，需要测试数据库预装 zhparser；该专项测试继续执行 `004_product_title_search.sql`。

```sh
buf lint
make proto
SAST_SHOP_TEST_POSTGRES_URL='postgres://.../postgres?sslmode=disable' \
WEST_POCKET_TEST_DSN='postgres://.../postgres?sslmode=disable' \
go test -race ./internal/pkg/... ./internal/service/userservice/... \
  ./internal/service/catalogservice/... ./internal/service/spotservice/... \
  ./internal/service/errandservice/... ./internal/service/paymentservice/... \
  ./internal/service/westpocketservice/...
make build
```

前端源 proto 从后端同步后执行仓库已有 `pnpm proto:generate`，再运行 API、desktop、mobile 的类型检查、测试、lint 和构建。飞书真实授权、真实收付款证据及生产网关连通性需要在部署环境验收。
