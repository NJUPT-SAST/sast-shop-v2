## 2. 总体实现方式

一句话：**Catalog 服务新增店铺分类树，商品模板上挂一个可空 `category_id`，前端按分类树取首屏与分页；分类的结构性写入统一走店铺级 PostgreSQL 事务 advisory lock。**

```text
浏览器
  └─ Next.js 服务端页面（SSR）
       listStores → listProductCategories → 按“默认分类”只取第一页模板
  └─ 客户端 ErrandShop（PC / 移动）
       切换一级/二级分类、关键词搜索 → listProductTemplatesPage(categoryFilterMode, categoryId)
  └─ 模板管理页
       分类筛选下拉 + 表单两级分类选择 + 新建/删除空分类
  └─ packages/api facade（ConnectRPC client）
       └─ catalogservice handler（requireCatalogMember + 错误映射）
            └─ service（校验、事务、advisory lock、模板分类联动）
                 └─ repository（bun / PostgreSQL catalog schema）
```

约定：

- 分类最多两级：一级 `parent_id IS NULL`，二级必须挂同店一级分类。
- 一级分类有子分类时，模板不能直接挂一级，必须挂其中一个二级；一级没有子分类时可直接挂一级。
- 建模板必须选分类；编辑历史未分类模板必须补分类；分类被物理删除，删前把已软删除模板的 `category_id` 置空。
- 前端只拿「当前选中分类」的第一页，不做全店拉取后本地过滤。

## 3. 数据库改动

### 3.1 新增迁移 `migrations/010_store_product_categories.sql`

新增表 `catalog.catalog_product_category`：

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `id` | `BIGINT` | `GENERATED BY DEFAULT AS IDENTITY` 主键 |
| `store_id` | `BIGINT` | 非空，`REFERENCES catalog.catalog_store(id) ON DELETE RESTRICT` |
| `parent_id` | `BIGINT` | 可空 |
| `name` | `TEXT` | 非空 |
| `sort_order` | `INTEGER` | 非空，默认 0 |
| `created_at` / `updated_at` | `TIMESTAMPTZ` | 非空，默认 `CURRENT_TIMESTAMP` |

约束与索引：

- `UNIQUE (store_id, id)`：供模板做复合外键引用。
- `FOREIGN KEY (store_id, parent_id) REFERENCES ... (store_id, id) ON DELETE RESTRICT`：父分类必须同店。
- `CHECK (parent_id IS NULL OR parent_id <> id)`：禁止自引用。
- `CHECK btrim(name) <> ''`、`CHECK char_length(btrim(name)) BETWEEN 1 AND 50`：名称非空且 ≤50 字符。
- 两个部分唯一索引：根分类 `(store_id, lower(btrim(name))) WHERE parent_id IS NULL`，子分类 `(store_id, parent_id, lower(btrim(name))) WHERE parent_id IS NOT NULL` —— 同级去空白后不区分大小写唯一。
- 树查询索引 `(store_id, parent_id, sort_order, id)`。

模板表改动：

- `catalog.catalog_product_template` 增加可空 `category_id BIGINT`。
- 复合外键 `(store_id, category_id) REFERENCES catalog.catalog_product_category(store_id, id) ON DELETE RESTRICT`：模板分类必须属于模板所在店铺。
- 查询索引 `(store_id, category_id, id)`。
- 保持可空以兼容存量数据；「新建必选 / 编辑补齐」由服务端强制。

迁移整体包在 `BEGIN; ... COMMIT;` 中，属增量脚本，不重跑初始化脚本，也不含数据回填（存量模板保持 `NULL`）。

- `ProductTemplateService` 增加三个 RPC 与对应消息：`ListProductCategories`（返回 `categories` + `has_uncategorized_products`）、`CreateProductCategory`（`store_id`、可选 `parent_id`、`name`）、`DeleteProductCategory`（`store_id`、`category_id`）。

分类 RPC 挂在既有 `ProductTemplateService` 上，复用原有路径与鉴权链，没有新建服务。

### 4.2 模型层 `internal/model/model.go`

- `CatalogProductTemplate` 增加 `CategoryID *int64 \`bun:"category_id"\``（指针表达 NULL）。

### 4.3 仓储层

`repository/catalog.go`：

- `ListProductTemplates` / `CountProductTemplates` 增加 `categoryFilterMode`、`categoryID` 参数，与 `filterProductTemplates` 共用同一过滤函数，保证列表与总数条件一致。
- 过滤语义：`CATEGORY(2)` → `category_id = ?` 或属于该一级的二级分类（子查询 `child.parent_id = ?`）；`UNCATEGORIZED(3)` → `category_id IS NULL`；`UNFILTERED(0/1)` → 不加过滤。

新增 `repository/product_category.go`：

- `ListProductCategories`：按 `parent_id ASC NULLS FIRST, sort_order ASC, id ASC` 一次取整棵树。
- `HasVisibleUncategorizedProducts`：按店铺可见性（模板非 removed、审核 `allowed`、店铺 `allowed` 且非 removed）统计是否存在未分类商品，供前端「未分类」虚拟入口使用。
- `GetProductCategory` / `GetProductCategoryForUpdate`：后者 `For("UPDATE")` 行锁。
- `HasDirectProductTemplates`：只统计 `status != removed` 的直接关联模板（包含被审核限制的未删除模板）。
- `HasChildProductCategories`、`NextProductCategorySortOrder`（同级 `MAX(sort_order)+1`）。
- `ValidateProductTemplateCategory`：分类不存在报错；分类是二级直接通过；一级则要求没有子分类。
- `ClearRemovedTemplateCategory`：删除分类事务内，把指向该分类的**已软删除**模板 `category_id` 置空。
- `CreateProductCategory` / `DeleteProductCategory`：纯插入/删除。

### 4.4 服务层

新增 `service/product_category.go`：

- 名称规范化：`TrimSpace` 后按 Unicode 字符数 1–50 校验。
- `ListProductCategories`：校验店铺 ID、店铺存在且未被封禁/删除，然后读分类树与未分类标志。
- `CreateProductCategory`：校验参数与名称 → 单事务内依次
  1. `pg_advisory_xact_lock(hashtextextended('catalog.product_category.store:<storeID>', 0))` 取店铺级分类锁；
  2. `requireStoreAvailable` 校验店铺可用；
  3. 有 `parent_id` 时校验父分类存在、同店、本身是一级、且该一级没有直接关联模板（有则拒绝加二级，即设计 3.1 第 4 条）；
  4. `NextProductCategorySortOrder` 计算同级末尾序号；
  5. 插入分类。
- `DeleteProductCategory`：同一把锁 + 同一事务，校验分类存在、无子分类、无未删除模板，先 `ClearRemovedTemplateCategory` 再物理删除分类。
- 错误映射：父分类有商品 → `FailedPrecondition`「该一级分类已有商品，暂不能添加二级分类」；三级 → `FailedPrecondition`「商品分类最多支持两级」；重名 → `AlreadyExists`「同级分类已存在同名分类」（靠 PostgreSQL 唯一索引名识别）；有子分类/有商品 → `FailedPrecondition`；分类不存在 → `NotFound`。
- `lockProductCategoryStores`：按店铺 ID 升序取多把锁，供模板跨店迁移使用，避免死锁。

`service/catalog.go`：

- `productTemplateToProto` 统一投影 `category_id`（详情、列表、条码查询、内部批量查询都走这一处）。
- `GetProductTemplateList`：新增 `validateTemplateCategoryFilter`。`CATEGORY` 必须带正数店铺与分类，且分类必须属于该店铺（否则参数错误）；`UNCATEGORIZED` 必须带店铺且不能带分类；`UNFILTERED/UNSPECIFIED` 不能带分类 ID。列表与计数使用同一过滤。
- `CreateProductTemplate`：`categoryID <= 0` 直接参数错误；写库前在事务中取分类锁、校验店铺可用、校验分类为「当前店铺的末级分类」。
- `UpdateProductTemplate`：
  - `FieldMask` 支持 `category_id`（值必须 > 0）；
  - 事务内先判断是否改分类或迁店，是则按当前店铺与目标店铺升序取分类锁；
  - 行锁读当前模板后校验：模板店铺未被并发改走（否则 `Aborted`「商品模板店铺已变更，请重试」）、版本时间、未分类模板必须补分类（`FailedPrecondition`）；
  - 需要时校验目标分类属于「更新后店铺」且是末级分类；
  - 普通字段（名称、价格、图片、条码）不取分类锁，仍只靠行锁 + `updated_at` 版本控制。
- `DeleteProductTemplate`：软删除前先查一次模板拿到店铺，事务内取该店铺分类锁、再行锁复核店铺未被改走，保证「删除模板释放分类占用」与分类并发操作同一协议。

`service/product_category.go` 中的 `lockProductCategoryStore` 被创建模板、更新模板、删除模板复用，锁协议集中在一处。

## 6. 设计规则 → 实现位置对照

| 设计规则 | 实现位置 |
| --- | --- |
| 分类两级、父级必须同店一级 | 迁移复合外键 + `validateCategoryParent`（父必须无 `parent_id`） |
| 同级去空白、忽略大小写唯一 | 两个部分唯一索引 + 服务端 `TrimSpace` + 冲突映射 `AlreadyExists` |
| 一级有子分类时模板必须挂二级 | `repository.ValidateProductTemplateCategory`（一级有子分类则拒绝），创建/编辑/迁店都调用 |
| 一级有直接商品时不能新增二级 | `CreateProductCategory` 内 `HasDirectProductTemplates`（含隐藏/待审未删除模板） |
| 有商品或有子分类不能删；空分类可删 | `validateCategoryDeletion`（先子分类、再直接模板） |
| 删分类时软删除模板置空 | `ClearRemovedTemplateCategory`（`status = removed`） |
| 分类写入的事务锁 | `pg_advisory_xact_lock(hashtextextended('catalog.product_category.store:<id>', 0))`；模板跨店按店铺 ID 升序取锁 |
| 普通字段编辑不被分类锁阻塞 | 只有改 `category_id` 或 `store_id` 才取锁；其余仍走行锁 + `updated_at` |
| 未分类虚拟入口 | 服务端 `has_uncategorized_products`（按可见性）+ 前端「未分类」按钮/入口，不是数据库记录 |
| 进入店铺默认第一个一级/第一个二级 | `getDefaultProductCategoryId` + 两端 SSR 首屏 |
| 切分类重置分页、保留关键词、不清购物车 | 两端 `loadPage(1)` + 关键词 state 不动 + 购物车独立 state |
| 列表与总数条件一致 | `ListProductTemplates` / `CountProductTemplates` 共用 `filterProductTemplates` |
| 现货嵌入模板店铺与分类一致 | `spot_goods.go` `templateForListing` 覆盖店铺时清空 `category_id` |
| PC 隐藏主导航、保留返回 | `desktop-shell.tsx` 路径匹配 + `errand-shop.tsx` 吸顶返回入口 |
| 离开未提交内容需确认 | 返回按钮 `confirm` + `beforeunload`（浏览器后退/站内路由跳转未覆盖，见第 8 节） |

## 8. 遗留问题与需要注意的点

1. **后台管理路径没有接分类。** `service/admin.go` 的 `applyAdminProductMutation` 直接 `repository.CreateProductTemplate`/`UpdateProductTemplate`，创建的商品 `category_id` 为 `NULL`，也不取分类锁；对已分类模板改 `store_id` 会因 `(store_id, category_id)` 复合外键不满足而写失败（对外表现为内部错误）。设计 §6 要求「后台操作改变分类占用时同样遵守锁协议」，这里尚未覆盖。
2. **分类删除没有二次确认。** 设计 §4.3 要求删除前确认；两端模板管理目前点击「删除所选分类」直接调接口，失败原因以 toast / 表单错误展示。
3. **离开确认只覆盖一部分离开路径。** 桌面店铺页对「返回团购工作台」按钮弹 `confirm`，刷新/关闭靠 `beforeunload`；浏览器后退和其他客户端路由跳转不会触发提示（Next 客户端导航不触发 `beforeunload`），这部分也没有单测。移动端店铺页的分类接口失败没有兜底（桌面有 `LoadFailure`），与改动前模板列表的行为一致。
4. **重名冲突依赖数据库报错文本。** `mapCreateCategoryError` 通过匹配索引名 `catalog_product_category_root_name_key` / `_child_name_key` 判断，数据库版本或语言设置变化会影响识别，后续可改为显式预检或错误码。
5. **强制分类没有过渡开关。** 服务端已直接要求新建/编辑必选分类（设计 §9 明说当前实现未加开关），旧客户端或未更新调用方写入会被拒绝，上线需按设计 §9 的顺序协调。
6. **前端分类 API 仅 `mock`/`local`。** 与现有 catalog facade 保持一致，`remote` 模式尚未放开。
7. **改动尚未提交/推送**，迁移也只在本地 15432 执行；交付前需要确认是否按批次提交（后端 proto 与 `migrations/` 建议先行）。
