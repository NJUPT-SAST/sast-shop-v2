# 店铺商品分类设计方案

日期：2026-11-23  
状态：设计草案，供评审

## 1. 目标与范围

为店铺商品模板增加最多两级的商品分类标签，按分类浏览商品，并在创建、编辑模板时选择或新增分类。分类属于店铺，一个模板只属于一个分类。移动端与 PC 端共享数据契约和业务规则，按各自交互实现页面。PC 店铺商品页隐藏左侧主导航，保留右上角“返回团购工作台”。本期实现普通用户能力，管理员分类管理和商品批量重新分配留待后续设计。

本文将聊天中称作“标签”的对象命名为商品分类，界面可以继续使用“分类标签”文案。以下将本仓库称为后端，`C:/program1/sast-shop-v2-frontend` 称为前端。

## 2. 已有项目基础

- 后端 `catalog.catalog_product_template` 已有 `store_id`、软删除状态和版本时间。`ProductTemplateService` 支持创建、更新和店铺维度的搜索分页，但没有分类字段。
- 活跃 `user`、`admin`、`superadmin` 可以维护目录。模板修改采用 `FieldMask` 和 `updated_at` 乐观并发控制，模板删除为软删除。
- 前端有独立的 `apps/mobile`、`apps/desktop`，共享 `packages/api`、`packages/domain` 和 `packages/ui`。两端店铺页面当前通过 `listProductTemplatesPage` 加载模板。PC 的 `DesktopShell` 负责主导航和内容列。
- 后端允许通过接口修改模板店铺，当前前端编辑界面锁定店铺。现货记录保留上架时的店铺，模板迁店后店铺可能不同。
- 后端 protobuf 契约位于 `proto/`，Go 服务目前使用 Buf 生成的远程模块依赖；前端使用 Buf 生成的 TypeScript 代码并通过 API facade 映射给页面。

## 3. 业务规则

### 3.1 分类和商品

1. 每个分类属于一个店铺。一级分类没有父分类，二级分类的父分类必须是同店铺一级分类，最多两级。
2. 没有二级分类的一级分类可以直接关联商品模板。有二级分类的一级分类不可直接关联模板，模板必须选择其中一个二级分类。
3. 创建模板必须选择分类；编辑模板必须有有效分类。表单必须先选择一级分类。一级有子分类时，用户须从该一级下明确选择一个二级分类，或在该一级下新建并选中二级分类。一级没有子分类时，可以直接保存到一级。
4. 某一级分类下已有直接关联的非删除模板时，普通用户不能为它新增二级分类，返回可理解的原因。管理员添加二级分类和重分配本期不提供。此规则包含隐藏或被审核限制的未删除模板，防止只统计前台可见商品造成破坏。
5. 某分类只要直接关联非删除模板，就不能删除。一级分类有任何二级分类时不能删除。分类被删除后其 ID 不复用。
6. 普通用户不能改名、调整排序、迁移分类或修改父分类。分类新增、删除要求活跃的目录成员身份；不依赖客户端传入角色。普通用户编辑、删除模板继续遵守已有权限。
7. 同店铺同一父分类内，去除首尾空白后的分类名唯一。大小写按数据库统一规范比较，一级分类之间和同一父分类下的二级分类之间分别约束。不同店铺或不同父分类可使用相同名称。名称长度建议 1–50 个 Unicode 字符，空白名拒绝。
8. 排序由服务端按同级末尾追加，默认按 `sort_order ASC, id ASC`；删除后允许序号有空缺。先按此规则解决默认分类，无需引入普通用户排序接口。
9. 分类创建成功后自动选中。模板保存失败时保留表单和已经创建的空分类，重复创建返回同名冲突并允许选择现有分类。分类删除或结构变化导致保存冲突时刷新分类并提示重新选择。

### 3.2 删除与历史模板

模板软删除后仍被历史记录引用。分类表不设状态字段，本期使用物理删除。删除分类事务中先验证没有子分类和非删除模板，再将指向该分类的已软删除模板的 `category_id` 置空，最后删除分类。其他模板和历史订单不删除。软删除模板分类置空不会用于重新展示，未来如支持恢复模板，恢复时必须重新选择合法分类。

分类删除、子分类创建及改变模板分类归属或占用状态的操作使用同一套事务锁。模板名称、价格、图片等普通修改不参与分类锁。第 6 节规定具体并发方案。

### 3.3 存量模板和无分类店铺

- 迁移时已有模板的 `category_id` 保持 `NULL`，不根据名称自动推断分类，也不自动创建普通分类。
- 店铺商品页将存在的历史未分类模板作为系统虚拟入口“未分类”，排在所有真实一级分类之后。它不是数据库分类，不能改名或删除。它仅在当前店铺有可见未分类模板时显示，使用独立筛选语义。
- 进入店铺优先选排序第一的真实一级分类；它有二级分类时默认选第一个二级分类。没有真实分类但有未分类商品时默认选“未分类”。两者都没有时显示空状态和创建分类入口。这是本方案为历史数据可见性作出的默认选择。
- 模板管理页可筛选和编辑未分类模板，编辑保存必须选择合法分类。历史未分类模板仍可沿现有方式被读取、下单及用于现货。

### 3.4 搜索、分页与购物车

进入店铺及切换分类时，先确定一级分类，再展示该一级下的二级选项。若有二级分类，默认选中其中排序第一项，用户可切换到同一一级下的其他二级项。切换一级时清除上一一级的二级选择，再按新一级的子分类确定默认项。若当前一级没有二级分类，直接展示该一级的商品。进入店铺不加载全店商品，首次请求只取最终选中分类的第一页。模板管理等其他调用方可用一级分类筛选汇总子分类商品。

关键词在当前选中分类内搜索。切换分类时分页重置为第一页，保留关键词并标明当前搜索范围。分页数据和总数使用完全一致的店铺、分类、关键词和可见性条件；分类、店铺、关键词、搜索模式和分页大小共同组成缓存身份。切换分类不清空购物车。

PC 右上返回按钮固定返回 `/group`。离开前若存在未提交购物车或正在编辑的需求草稿，提示用户确认放弃；取消后留在当前页。浏览器后退、站内链接、刷新或关闭页面等离开路径也需要尽可能覆盖，其中刷新/关闭使用浏览器支持的原生提示。提交成功后的程序跳转不触发误提示。提示实现需与已有的采购需求编辑和未完成提交恢复流程协调，不能重复提交或丢失状态。

## 4. 页面设计

### 4.1 PC 店铺商品页

```text
店铺名称                                    返回团购工作台
────────────────────────────────────────────────────────────
一级分类       二级分类和搜索                       购物车
  食品         [薯片] [饼干] [饮料]  [搜索商品]      已选商品
  日用品       商品卡片  商品卡片                   数量、金额
  文具         商品卡片  商品卡片                   提交
  未分类
```

店铺页隐藏 `DesktopShell` 的主导航列并释放其宽度，店铺标题、返回入口、分类、商品列表和购物车保持可用。返回工作台后恢复主导航。返回入口在商品区域滚动时仍可访问。窄窗口允许购物车调整为下方区域，保留键盘操作和焦点状态。

### 4.2 移动端

沿用移动端导航和抽屉交互。店铺内显示一级分类选择和二级分类切换，默认选择及数据规则与 PC 一致；模板表单通过 Drawer 选择或新建分类。小屏和键盘弹出时，分类和保存操作仍可触达。

### 4.3 模板管理与分类维护

两端模板表单先选店铺，再选一级分类。一级选定前，二级选择不可用。选定一级后，二级候选仅来自该一级。如果有二级分类，必须由用户选择，表单不会自动选排序第一项。编辑时回显已有的有效分类路径，新建二级成功后自动选中该项。没有分类时可新建一级，选中允许添加子分类的一级后可新建二级。切换店铺清除两级选择，切换一级清除旧二级选择。分类创建和删除入口应有明确的店铺上下文，删除前确认；有商品或子分类时展示后端原因。分类列表变更后刷新本店的分类树、商品列表和模板管理缓存。

## 5. 数据库设计

新增按现有顺序编号的迁移，预计为 `migrations/010_*.sql`，落地时确认编号未被占用。已有环境执行增量迁移，不重跑初始化脚本。

### 5.1 `catalog.catalog_product_category`

| 字段 | 类型 | 约束及用途 |
| --- | --- | --- |
| `id` | `BIGINT` | identity 主键 |
| `store_id` | `BIGINT` | 非空，引用 `catalog.catalog_store(id)` |
| `parent_id` | `BIGINT` | 可空，一级为空，二级关联同店铺一级分类 |
| `name` | `TEXT` | 非空，服务端去空白并限制长度 |
| `sort_order` | `INTEGER` | 非空，同级排序 |
| `created_at` | `TIMESTAMPTZ` | 创建时间 |
| `updated_at` | `TIMESTAMPTZ` | 更新时间，供后续维护使用 |

按需求不增加 `status` 和 `created_by_user_id`。数据库外键采用限制删除，不级联删除分类或模板。建议定义 `(store_id, id)` 唯一键，并通过 `(store_id, parent_id)` 复合外键约束父分类同店铺；`parent_id IS NULL OR parent_id <> id` 防止自引用。父级必须是一级、不可添加第三级，需要服务端事务校验。

为根分类和子分类分别建立部分唯一索引，根分类按 `(store_id, lower(btrim(name))) WHERE parent_id IS NULL`，子分类按 `(store_id, parent_id, lower(btrim(name))) WHERE parent_id IS NOT NULL`。这样无需依赖 PostgreSQL 新版本的 `NULLS NOT DISTINCT`。数据库校验同时限制去空白后非空及长度；索引与服务端大小写规范保持一致。排序和树查询使用 `(store_id, parent_id, sort_order, id)` 索引。

### 5.2 `catalog.catalog_product_template`

新增可空 `category_id BIGINT`。以 `(store_id, category_id)` 复合外键引用分类 `(store_id, id)`，保证分类与模板同店铺。`NULL` 用于迁移后的历史未分类模板，以及已软删除模板清除分类引用后的状态；新模板和编辑保存必须在服务端校验非空。增加 `(store_id, category_id, id)` 查询索引，并评估现有可见性条件下的执行计划。

字段保持可空是为了兼容存量数据；“新建必选”和“编辑补齐”属于服务端业务约束。若未来数据迁移完成、软删除策略变化，再另行评估数据库 `NOT NULL`。

## 6. 一致性、权限和并发

所有公开分类写入复用现有会话鉴权与 `requireCatalogMember`，包括普通用户、管理员角色均按本期普通用户规则处理，不通过用户输入判断管理员身份。本期不提供分类更新 RPC。授权、店铺可用性和数据校验都由服务端执行。

Catalog service 在写事务中获取 PostgreSQL 事务级 advisory lock，例如 `pg_advisory_xact_lock(hashtextextended('catalog.product_category.store:' || store_id::text, 0))`。固定前缀区分分类用途，并为完整的 `BIGINT` 店铺 ID 生成锁键。哈希碰撞只会使本可并行的请求额外等待。数据库在提交或回滚时自动释放锁。分类操作无需为互斥而锁住 `catalog.catalog_store` 的整行，现有店铺可用性校验继续使用原来的锁。

新增或删除分类、创建或软删除模板、修改 `category_id`、模板迁店及其他改变分类占用的操作须取得该锁，再用同一个 `tx` 查询和写入。模板跨店铺迁移按店铺 ID 升序获取两把分类锁，再锁定模板行并核对源店铺。如果等待期间模板已迁店，当前事务回滚并返回冲突，调用方刷新后可以重试。后台操作和数据修复如果改变分类占用，也须遵守这一顺序。数据库外键与唯一索引提供额外约束。

只改名称、价格、图片等字段时，沿用单个模板的行锁、`updated_at` 版本校验和原有店铺可用性校验。强制分类启用后，锁定模板行再检查现有分类是否为空。已分类的模板可以直接保存普通字段，历史未分类模板须补选分类后再提交，并走分类加锁路径。同一模板上的并发编辑仍可能因行锁或版本冲突而等待或失败。

创建首个子分类与模板直接归属一级分类，删除分类与模板引用、创建子分类，必须在锁内检查。并发请求中后一事务看到前一事务结果并重新校验。删除分类时处理软删除模板引用也在同一事务完成。修改模板沿用 `updated_at` 和 `FieldMask`，检查的是更新后的店铺与分类组合；只改店铺时若旧分类不属于目标店铺，应拒绝并要求同时指定目标店铺的有效分类。考虑现有前端锁店铺，仍须保护其他接口调用方。

现货展示中，模板迁店可能导致现货原店铺与模板分类店铺不同。分类本期用于店铺模板浏览，不用于现货列表筛选。返回现货嵌入模板时，若为了保留旧行为将模板 `store_id` 改为现货原店铺，应同时清除不属于该店铺的 `category_id`，避免返回自相矛盾的数据。历史订单与采购快照不因分类修改而重写。

## 7. Proto 和接口设计

以 `.proto` 作为唯一 RPC 契约，扩展后使用 Buf 生成 Go 和 TypeScript 接口代码。前端已有 facade 可继续将 ID、时间映射为适合页面的类型，不手写生成代码。新增字段使用新的 protobuf 字段号，不改原字段编号。

### 7.1 分类服务

在 `proto/sast/sastshopv2/catalog/v1/` 增加分类消息，并将以下 RPC 注册到现有 `ProductTemplateService`。这两个资源由同一 Catalog 服务维护，可以沿用现有鉴权和网关路径。

| RPC | 请求 | 返回及规则 |
| --- | --- | --- |
| `ListProductCategories` | `store_id` | 返回店铺分类及父子关系、排序字段；服务端稳定排序，包含判断未分类入口所需的可见未分类存在标志 |
| `CreateProductCategory` | `store_id`、可选 `parent_id`、`name` | 返回新分类；同级末尾排序，服务端验证店铺、父级、名称和直接商品约束 |
| `DeleteProductCategory` | `store_id`、`category_id` | 删除空分类；验证请求店铺和分类归属、子分类及商品引用 |

分类树按店铺一次读取。前端根据 `parent_id` 在一级选定后列出该一级的二级分类，无须为每次切换一级另发一次分类查询。商品列表请求仍使用最终选中的分类 ID。新建二级时，`parent_id` 必须是当前选中的同店铺一级分类 ID，由后端验证。普通客户端无需接收被审核限制的商品明细。`has_uncategorized_products` 应按店铺商品页可见性计算，避免泄漏隐藏商品；删除判断使用更严格的未删除模板范围。

### 7.2 商品模板服务

- `ProductTemplate` 新增可选 `category_id`，缺省代表历史未分类。所有模板读取路径，包括详情、列表、条码查询和内部批量查询，统一映射该字段。
- `CreateProductTemplateRequest` 新增 `category_id`；启用强制校验后新建必选。
- `UpdateProductTemplateRequest` 复用 `ProductTemplate` 和 `update_mask`，支持 `category_id`。编辑旧模板时，服务端根据更新后的完整对象检查分类，缺失则返回需要补分类的业务错误。
- `GetProductTemplateListRequest` 通过 `category_filter_mode` 区分默认或全部、指定分类和未分类。指定分类时传 `category_id`，一级包含自身和二级分类的商品，二级只查自身。未分类查询 `category_id IS NULL`。指定分类或未分类筛选时必须指定店铺，分类与店铺不匹配返回参数错误。
- 列表查询与计数复用同一过滤函数，保留现有分页上限、搜索语义和稳定排序；页面不通过全量拉取后本地过滤。

错误需能区分未登录、无权限、店铺或分类不存在、名称冲突、层级不合法、分类含子分类或商品、分类已变更、模板版本冲突。可复用现有业务错误机制和 Connect 状态码，并在 facade 映射为用户可理解的提示。

## 8. 代码结构改动

### 8.1 后端

- `migrations/` 新增迁移，建立表、约束、索引和模板分类列。
- `internal/service/catalogservice/internal/model/` 增加分类模型及模板字段。
- `internal/service/catalogservice/internal/repository/` 实现分类查询、锁内读写，以及模板分类筛选和计数。
- `internal/service/catalogservice/internal/service/` 实现校验、事务、锁顺序和模板分类映射；检查目录管理与模板删除、迁店等已有写入。
- `internal/service/catalogservice/internal/handler/v1/` 注册分类服务、执行鉴权和错误映射，扩展模板 handler。
- `internal/service/spotservice/` 处理模板迁店后返回现货嵌入模板的店铺与分类一致性。
- proto 增量修改并按项目的 Buf 流程同步 Go 生成模块版本和前端生成代码，保证构建使用的新契约一致。核对现有网关、Connect 代理的路由白名单，将新分类服务纳入现有鉴权链，并验证 mock/local 和线上入口都可访问。

### 8.2 前端

- `packages/api/src/services/` 增加分类 facade，扩展模板类型、参数校验、筛选和映射。`packages/api/src/gen/` 由 Buf 生成。
- `packages/domain/` 仅放两端确实共享的分类选择、默认项和纯规则。`packages/ui/` 放能共享的基础控件，避免强行统一两端容器。
- 移动和 PC 的 `product-template-manager` 接入分类树、选择、新建与删除；保留现有表单、版本冲突和错误恢复逻辑。
- 两端店铺 `group/shop/[id]` 与 `errand-shop` 使用分类树及选中分类首屏数据，后续按分类、关键词分页；新增缓存刷新和空状态。
- PC `DesktopShell` 和路由布局增加店铺页的无主导航布局，只影响 `/group/shop/[id]`。保留 `AuthBootstrap`、协议 provider、刷新组件和现有页内滚动语义，不能通过简单遮盖侧栏保留空白列。店铺路由加载、错误和不存在状态也需能返回工作台。
- 同步 `mock/fauxrpc/stubs/`、本地 proto schema 和相关类型/数据，让 mock 与真实服务遵循一致规则。

## 9. 兼容、发布与回退

新增 protobuf 字段兼容旧读取方。当前本地实现已强制要求新建模板选择分类、编辑未分类模板时补齐分类，因此旧前端写入可能失败。远程发布前需要明确升级顺序。下面是需要保留新旧客户端并行时的可选发布方案，当前实现没有加入过渡开关。

1. 数据库迁移先落地，旧记录保持 `NULL`。
2. 发布支持新字段、筛选及分类服务的兼容后端，暂不对旧客户端强制新建和编辑必选。必须具备可控的服务端发布开关或等效部署机制，并记录兼容窗口内新增的未分类模板。
3. 同步 Buf 契约版本并发布两端前端，确认所有受支持的写入入口均发送分类。旧客户端未退出、其他调用方未更新时，保持兼容窗口并监控未分类新增。
4. 验证前端及其他调用方已升级后启用强制校验。窗口内未分类模板与历史模板按“未分类”展示并逐步补齐。

兼容窗口属于过渡期，不能宣称期间所有新建均强制分类。若无法控制或识别旧客户端，强制启用的时间需由发布负责人依据客户端淘汰情况决定。回退前端时先关闭强制校验；回退后端或数据库前核查新增数据和依赖，保留可空列及分类数据以便恢复，具体数据库回退脚本需在实施时演练。

## 10. 测试与验收

- 数据和权限：同店同级重名、跨店父子关系、三级分类、非法 ID、未登录/非活跃身份、分类改名和排序入口不可用；普通用户不能绕过服务端限制。
- 规则：一级有直接商品时拒绝加二级；有子分类时拒绝把商品直接关联一级；有商品或子分类时拒绝删除；空分类可删；软删除模板引用清理后分类可删且历史记录保留。
- 并发：添加首个二级与创建一级商品、删除分类与新增或改归属模板、删除一级与创建子分类、跨店迁移并发执行，结果始终满足约束。保持分类事务打开时，验证同店其他模板的改价或改图不等待分类锁，并检查同一模板的并发修改仍受版本控制。
- 兼容：历史 `NULL` 分类、只含未分类的店铺、旧客户端兼容窗口、强制启用后的旧写入失败、模板版本冲突、现货模板迁店后分类字段一致。
- 查询：默认首分类和首子分类、切换一级时重置二级并只展示新一级的子分类、一级/二级/未分类筛选、关键词与分页及总数、分类切换缓存隔离、分类变化后的刷新。
- 两端：模板表单先选一级再选二级，切换一级时清除旧二级，有二级时用户须明确选择，编辑回显路径，新建成功后选中，分类创建失败和删除失败时保留表单，空状态；PC 隐藏导航后直接访问、加载/失败/不存在页面、窄宽窗口、键盘、购物车和离开确认；移动端小屏和输入法。
- 实施后运行后端相关测试及前端 lint、typecheck、受影响行为测试和构建，核对 Buf 生成物与 mock。真实客户端和数据库迁移验证的环境与结果单独记录。

## 11. 技术取舍与待确认项

- **一张自关联分类表 + 模板单个分类 ID**：两级树简单，分类归属唯一；未来需要多分类时另建关系表，避免本期多对多复杂度。
- **物理删除 + 历史软删除模板置空**：满足不设分类状态字段，并使无有效商品的分类可删除；保留分类名称历史的审计能力未纳入本期，如需追溯应另行设计审计记录。
- **分类事务锁**：同店铺仅涉及分类结构、归属或占用的写入使用同一把 PostgreSQL advisory lock。普通模板字段编辑继续按模板控制并发。这避免把店铺行当作分类互斥锁，但要求所有能改变分类占用的写入都遵守同一协议。
- **未分类虚拟入口**：保证历史商品可见且不伪造真实分类；默认优先真实分类，属于本文建议，需产品确认。
- **用户分类维护权限**：本文按现有目录共同维护权限允许所有活跃成员创建及删除空分类，禁止修改分类。是否需要进一步限定谁能删除他人创建的空分类，请产品确认。由于分类表不保存创建者，若需按创建者授权，需要另行设计可信的归属数据。
- **搜索范围**：本文建议保留关键词并限定当前分类，属于交互默认值，需产品确认。
- **范围**：本期分类筛选覆盖店铺模板浏览及模板管理，不扩展跨店铺现货商城的分类筛选。若现货也需要分类浏览，需要单独确定跨店分类及模板迁店后的分类归属。
